# Dataset and Data Preparation

## Source and version

The project uses **Office-Home**, introduced by Venkateswara et al. (CVPR 2017). It contains 15,588 images, 65 object classes, and four domains: Art, Clipart, Product, and Real_World. The same 65 class names apply across all domains.

- Official dataset page: https://www.hemanthdv.org/officeHomeDataset.html
- Original distribution: `OfficeHomeDataset_10072016.zip`.
- Download source used in the experiment: https://huggingface.co/datasets/flwrlabs/office-home
- Exact mirror revision: `2a083645e3177afbd91ba4fa2651238f8994d335`.
- Version-pinned files: https://huggingface.co/datasets/flwrlabs/office-home/tree/2a083645e3177afbd91ba4fa2651238f8994d335/data

The mirror supplies three Parquet shards with embedded image bytes, domain names, and class labels. The notebook verifies the shard sizes and SHA-256 checksums before extraction. The download source is a mirror; the official dataset page remains the authoritative source for dataset terms.

## Data validation and deduplication

1. Extract the shards in their declared order without re-encoding image bytes.
2. Verify that every domain contains the same 65 class names. Use alphabetically sorted class names to construct the common label mapping.
3. Decode each image with Pillow and verify that it can be converted to RGB.
4. Compute SHA-256 over the original encoded image bytes. Remove exact duplicates globally **before** partitioning, keeping the first image in domain order `Art`, `Clipart`, `Product`, `Real_World` and sorted relative-path order within each domain.
5. Preserve the relative path, domain, class name, integer label, and image checksum in the split manifest.

The completed experiment rejected **0 corrupt images** and removed **412 duplicate copies**, leaving **15,176 images**. Nine removed copies had a retained counterpart in another domain. This procedure detects exact byte duplicates; it does not detect visually similar images or differently encoded copies.

## Partition and experimental use

Partition images independently within each `(domain, class)` group, after deduplication. Use a single NumPy `default_rng(2026)`, traverse groups in sorted order, sort each group's relative paths, and permute their row indices. Set validation and test counts separately to `max(1, int(round(n * 0.15)))`; assign the first indices to validation, the next indices to test, and the remainder to training. The approximate ratio is 70/15/15, with per-class rounding.

| Domain | Train | Validation | Test | Total |
|---|---:|---:|---:|---:|
| Art | 1,617 | 349 | 349 | 2,315 |
| Clipart | 2,960 | 646 | 646 | 4,252 |
| Product | 2,985 | 646 | 646 | 4,277 |
| Real_World | 3,030 | 651 | 651 | 4,332 |
| **Total** | **10,592** | **2,292** | **2,292** | **15,176** |

All four domains retain all 65 classes in every partition. Only **Real_World training** images update model parameters. **Real_World validation** macro-F1 selects checkpoints and determines early stopping. Final evaluation uses the four test partitions. Target-domain training and validation partitions are not used for fitting, selection, or tuning. This is a custom source-only held-out protocol, rather than the standard Office-Home domain adaptation protocol.

## Image preprocessing

Images are converted to RGB at loading time. Training transformations use torchvision `RandomResizedCrop(224, scale=(0.7, 1.0))`, `RandomHorizontalFlip()` with default probability 0.5, `ToTensor()`, and ImageNet normalization. Validation and test transformations use `Resize(256)` on the shorter edge, `CenterCrop(224)`, `ToTensor()`, and the same normalization.

Normalization mean: `[0.485, 0.456, 0.406]`. Standard deviation: `[0.229, 0.224, 0.225]`. Augmentation applies only to the source training partition. Transformations are applied in memory; augmented images are not exported as a separate dataset. The recorded training environment used torchvision `0.26.0+cu130`.

## Reproducing the experiment data

The complete data preparation code is provided in [`OfficeHome_DomainShift_Colab_T4.ipynb`](OfficeHome_DomainShift_Colab_T4.ipynb). The notebook is the executable reproduction entry point; no additional data preparation script is required.

1. Open the notebook in Google Colab and select a T4 GPU runtime. The notebook's environment check requires CUDA, although acquisition and partitioning themselves run on the CPU.
2. Run Sections 1–2 in order to install dependencies and initialize the configuration. Keep `SPLIT_SEED = 2026`, `CHECK_EXACT_DUPLICATES = True`, and `SMOKE_TEST = False`.
3. Run Section 3, **Automatic dataset acquisition**. It downloads the three version-pinned Parquet shards, verifies their sizes and checksums, and extracts their original image bytes. No Google Drive mount, authentication, or manual archive upload is required.
4. Run Section 4 to validate images, remove exact duplicates globally, create the shared label mapping, and generate the stratified partitions.
5. Run the data-loader cell in Section 5 to define the training and evaluation transformations. Subsequent experiment sections train and evaluate the models using these partitions.

Extracted images are stored under `/content/officehome_data/officehome_hf/`. The notebook exports the following records to its run-specific directory under `/content/OfficeHome_DomainShift_T4/`:

| Record | Contents |
|---|---|
| `split_manifest.csv` | Relative image path, domain, class name, integer label, image SHA-256, and split assignment |
| `class_to_idx.json` | Common mapping for the 65 classes |
| `exact_duplicates_removed.csv` | Removed image paths and their retained counterparts |
| `rejected_images.csv` | Image rejection log; empty in the completed experiment |
| `config.json` | Dataset revision, partition seed, manifest digest, and experiment configuration |

The completed run was identified as `run_5765dc922429`. Its identifier also depends on software versions and other configuration values, so a different environment may produce a different directory name. Data equivalence is established by the manifest digest and split counts above. Section 4 computes the digest and records it in `config.json`.
